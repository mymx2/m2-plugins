# Public Reply Mode (GitHub issue / PR)

Loaded from `write` when the deliverable is a maintainer reply on a public issue or PR thread; the request names the issue or PR and may ask for the comment text.

The reply shape, ship-state vocabulary, next-step rules, posting/editing mechanics, and closure criteria are owned by the `check` skill's `public-reply` reference — the single source. Read it before drafting; do not restate its rules here. This mode adds only the composition-side rules below.

1. **One paragraph and one or two sentences by default.** Two short paragraphs are the exception, used only when a one-line command or necessary ambiguity cannot fit cleanly. No bullet lists, section headers, or code blocks except that one-line command.
2. **A batch of replies is N replies, not one skeleton filled N times.** When closing or answering several threads in one pass, read the drafts side by side before posting: same opening clause, same paragraph order, and same closing move across three or more of them reads as template voice no matter how correct each one is. Only the facts are shared. The opening sentence in particular should come from that thread's own report.
3. **The reply is the final user-facing text, not an agent log.** Do not write "刚才我判断错了", "前面回复有误", "I re-read it and changed the comment", or any meta narration about your own process. If editing an existing maintainer comment, replace it with the clean final wording as if it were the only comment the user will read.
4. **Paid / subscribed users:** acknowledge the purchase relationship and the inconvenience in one phrase, then state the boundary. Do not over-explain. When the current product cannot support their setup, suggest the safest practical path (upgrade macOS, wait for the next release, provide logs, refund route) without arguing.
5. **Private support channels** (DM, in-app reply, support email): drop the report register entirely — short colloquial sentences in the maintainer's own voice, lead with what the user gets rather than how it works, and fewer full stops than documentation would carry.
6. **Closing comments stand alone.** When closing as `completed`, the comment must independently explain what was fixed and the expected release. When closing as `not planned`, it must independently explain the current boundary and an alternative path. Do not rely on prior thread context as the explanation.
