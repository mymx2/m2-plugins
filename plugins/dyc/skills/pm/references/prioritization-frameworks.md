# 优先级排序框架

本文件是优先级框架定义的正本；think 技能的 prioritization reference 引用本文件，不重复定义。

给 backlog、需求列表、功能候选排序时加载。与 think 技能的 prioritization reference 配套——那边把框架当工程决策辅助，本文件补 PM 侧的产出契约：评分表、决策日志、容量砍削顺序。

## 框架选择

按数据充分度和决策场景选，不按习惯：

| 条件                                       | 框架       | 理由                       |
| ------------------------------------------ | ---------- | -------------------------- |
| 有可信的逐项影响数据（触达、转化率、用量） | **RICE**   | 最量化、最可审计           |
| 有一定感知但缺精确数字                     | **ICE**    | 打分快，容忍主观性         |
| 团队对齐会，要快速分四档                   | **MoSCoW** | 逼出"必须做"和"不做"的共识 |
| 要理解需求性质、做功能规划                 | **Kano**   | 区分及格线功能和惊喜功能   |

说明选了哪个、为什么。打到一半发现数据比想的薄，就降级框架（RICE → ICE → MoSCoW）并说明。

## 打分

### RICE

`得分 = (Reach × Impact × Confidence) / Effort`

- Reach：写每周期具体数字（"月影响 5000 人"）
- Impact：3=巨大 / 2=高 / 1=中 / 0.5=低 / 0.25=极低
- Confidence：100%=有数据 / 80%=间接证据 / 50%=直觉
- Effort：全链路人月——设计 20% + 开发 50% + 测试 20% + 联调 10%

### ICE

每项 1-10 分，`得分 = I × C × E / 10`。Ease 10=<1 天，5=2-4 周，1=>3 个月。

### MoSCoW

| 档位          | 判断标准                                  | 占比建议 |
| ------------- | ----------------------------------------- | -------- |
| Must          | 没有就不能上线，核心流程断                | ≤60%     |
| Should        | 重要但有 workaround，延一个 Sprint 不致命 | ~20%     |
| Could         | 锦上添花                                  | ~10%     |
| Won't（本期） | 明确不做，未来可能做                      | ~10%     |

Must 超 60% 是经典失败；强制卡线，超出的部分就是框架要逼出来的取舍对话。

### Kano

基本型（没有会不满，有了理所当然——做到及格线，不过度投入）/ 期望型（做得越好越满意，线性——核心竞争力，做到行业前列）/ 兴奋型（没有不不满，有了惊喜——差异化亮点，但会随时间退化为期望型）/ 无差异型（不投入）/ 反向型（做了反而降满意度，移除）。

## 校准反偏差四规则

1. 先把所有需求的同一维度集中打完（先打完所有 R，再打所有 I），逐需求打分会锚定。
2. 选一个基准需求（如"登录影响所有用户"），其他需求与之对比打分。
3. 强制拉开差异：打最高 Impact 分的需求不得超过一半。
4. Effort 必须含全链路。Confidence <80% 的需求标"建议先做小实验验证"，带标参与排序。

## 产出契约

1. **评分表**：排名、需求、各维度得分、总分、每分一句话依据。没有依据的分无法被挑战，无法被挑战的分每次开会都会被重吵。
2. **影响 × 工作量四象限**：Quick Wins（优先做）/ Big Bets（规划做）/ Fill-ins（有空做）/ Money Pits（不做）。
3. **分配**：Quick Wins 优先填入，Big Bets 按得分排序进，每个迭代留 10-20% 缓冲应对突发。
4. **决策日志**：核心取舍（为什么选 A 不选 B）、争议需求及争议点、每个 Confidence<80% 的分及其验证建议、Won't 里下期最可能晋升的候选。

## 容量砍削顺序

容量不足时按此顺序逐级砍：先砍 nice-to-have → 再把需求拆半、延后后半段 → 再降低存活项的完美度。砍 scope 永远优于延期，延期永远优于加人。

## 红线

- 排序结果是建议不是决定——最终优先级由团队对齐，明说这一点。
- 不隐藏假设：每个打分的前提在表里可见。
- 不许只看 Impact 不看 Effort 就推"必做"。
