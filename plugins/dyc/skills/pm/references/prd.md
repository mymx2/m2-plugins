# PRD 与故事拆解

写 PRD、功能规格、需求文档，以及把 Epic 拆成带验收标准的用户故事时加载。

## PRD 模式

### 产品类型分支（先选，并说明选了哪个）

| 类型     | PRD 侧重                           | 必须额外覆盖                                                             |
| -------- | ---------------------------------- | ------------------------------------------------------------------------ |
| B2C      | 用户体验流程、增长指标、实验方案   | 用户旅程、参与闭环                                                       |
| B2B      | 功能完备性、安全、集成             | 权限矩阵（角色 × 功能 × 数据范围）、多租户隔离、集成接口清单             |
| 内部工具 | 操作效率、与现有系统集成、培训成本 | 具体操作流程；视觉打磨不在范围内                                         |
| 平台型   | 多角色交互、供需匹配、生态规则     | 各角色（供方/需方/平台运营）独立功能视角、匹配与排序规则、佣金与结算规则 |

未指定时按词汇推断（会员/积分/商城 → B2C；企业/SaaS/后台 → B2B；内部/工单 → 内部工具；平台/撮合/双边 → 平台型），并说明这是推断。

### 需求拆解（三遍法，可组合）

1. **用户旅程法**：画出用户从入口到完成目标的完整路径，每个节点是一个功能点。
2. **角色拆分法**：列出所有涉及角色（终端用户、管理员、运营），每个角色的操作是一个模块。
3. **CRUD 法**：对每个核心数据对象，穷举创建/读取/更新/删除四类操作。

每个功能模块填：一句话功能描述、用户故事（作为[角色]，我希望[操作]，以便[价值]）、业务规则、交互流程（入口 → 步骤 → 成功/失败反馈）、异常处理（每个功能至少 2 个异常场景）。

### 文档骨架

开头先放文档信息块：产品名、版本号、日期、编写人、审核人、版本变更记录表（版本/日期/摘要/修改人/审核人）。多轮评审的文档没有版本记录，团队会对照着过期草稿吵架。

正文按序：

1. **文档概述**：本文档解决什么业务问题、对齐什么决策；阅读对象是谁；术语与缩略语表（业务黑话、系统缩写统一口径）。
2. **背景与目标**：为什么现在做、不做会怎样、做了能怎样；业务目标每个都 SMART（有数字、有截止时间、有监测方式），并单列"成功衡量标准"——上线后依据什么核心数据判定"做成了"，含观测指标、观测周期、达标阈值。
3. **目标用户与场景**：角色+特征+场景表（每个角色具体可识别，落到人群画像而非"所有用户"）；2-3 个核心业务场景，每个按"【角色】在【什么条件下】为了【什么目的】，当前遇到【什么阻碍】，本项目通过【什么方案】解决"写。
4. **需求范围与边界**：本期包含（In-Scope）/ 本期不包含（Out-of-Scope，明确列出不做的事，防范围蔓延）/ 后续迭代方向 / 前置依赖与约束（依赖的系统、资质审批、预算人力硬约束，无则写"无"）/ 存量处理（存量数据迁移方式、存量用户过渡方式、切换窗口与回退条件，全新项目写"不涉及"）。
5. **功能详设**：各功能模块（见下"功能定义卡片"）。
6. **核心业务规则与策略**：最关键的业务判断/计算/分配逻辑；主流程走不通时的异常与兜底策略。
7. **非功能需求**：性能/安全/兼容性，带验收阈值（技术指标定义法见下）。
8. **数据与运营**：数据埋点（事件名+触发条件+属性+用途）；上线推广方案（外部产品看获客激活，内部系统看培训通知切换）；用户支持方案（支持渠道、响应时效、问题升级流程）。
9. **验收标准**：Given-When-Then，每个模块 ≥3 条。
10. **计划与协同**：排期（开发/测试/联调/UAT/上线，带工时与风险）；跨部门协同需求（法务/财务/市场/客服运维，各配合什么、什么节点）；上线策略（全量/分批/试点，是否新老并行，观测期与正式确认节点）。
11. **风险与依赖**：风险矩阵表（风险项/影响程度/发生概率/应对预案/责任人），业务合规风险与技术资源风险分列。

### 功能定义卡片（每个核心功能一张）

| 项目                         | 内容                   |
| ---------------------------- | ---------------------- |
| 功能ID / 名称 / 所属模块     | FUNC-XXX 编号便于追踪  |
| 功能描述                     | 一句话做什么           |
| 用户价值                     | 解决什么痛点           |
| 前置 / 后置条件              | 使用前提与用后系统状态 |
| 正常流程                     | 1. 2. 3. 编号步骤      |
| 异常流程                     | 错误处理与边界         |
| 验收标准                     | 可量化的完成定义       |
| 优先级 / 依赖项 / 预计工作量 | P0/P1/P2，人天或故事点 |

### 技术指标定义法（非功能需求章节用）

1. **选维度**：性能、可靠性、体验、成本、合规五类里筛关键质量属性。
2. **量化**：每个指标必须有数值、单位、测量方法。"响应快"不是指标，"首字节 <200ms（压力测试）"才是。
3. **三级定义**：目标值（Target）/ 挑战值（Stretch）/ 底线值（Threshold），不接受单一数字。

### MVP 范围划定

三个判定必须同时满足：能验证至少一个核心假设 / 能让用户端到端完成核心任务 / 能量化用户价值。

排除清单（不纳入 MVP）：不验证核心假设的装饰功能、可被临时方案（人工/线下/第三方工具）替代的功能、只提升体验不影响可用性的优化、面向非核心用户的功能、需要大量基建但非即刻必需的功能。

决策流程逐问：能被临时方案替代吗？（能→排除）→ 验证核心假设或支撑核心任务吗？（否→排除）→ 面向核心用户吗？（否→推到 V1.0）→ 在时间预算内吗？（否→拆分或简化）。检查清单：用户能用 MVP 完成核心任务闭环？有可测的成功指标？周期在 8-12 周内？发布后 2 周内可迭代？

### 质量门（12 项全过才算完）

1. 背景回答了"为什么做"，不是只说"需要做"
2. 至少一个数字型成功指标
3. 用户表里没有"所有用户"
4. 业务规则穷举，无"等"、"其他情况"
5. 每个功能至少 2 个异常场景
6. 验收标准是 Given-When-Then 格式
7. 核心操作路径都有埋点
8. 全文零技术实现（不写数据库、框架、架构选型）
9. 每个模块标了 P0/P1/P2
10. 工时评估含开发+测试+联调
11. Out-of-Scope 显式列出（不是只有 In-Scope）
12. MVP 项同时过三判定（验证假设/完成核心任务/可量化价值）

### 反模式

| 反模式   | 表现                                | 正确做法                                          |
| -------- | ----------------------------------- | ------------------------------------------------- |
| 需求镀金 | 一期写 50 个功能点                  | 拆 MVP / v1.1 / v2；MVP 聚焦 3-5 个功能           |
| 伪需求   | "用户可能需要..."没有数据或调研支撑 | 标注需求来源：用户反馈/数据分析/竞品参考/业务判断 |
| 交互越界 | PRD 里写按钮颜色、字号、布局        | 只描述信息层级和交互逻辑，视觉交给设计            |
| 技术越界 | PRD 里指定用 Redis、MySQL           | 只写性能要求（如"<2秒"），实现交给技术            |
| 规则黑洞 | "按业务规则处理"但不写规则          | 穷举每条规则的触发条件、处理逻辑、边界值          |

## 故事拆解模式

### 选拆分模式（说明选了哪种）

| 拆分模式           | 适用场景           | 示例                                      |
| ------------------ | ------------------ | ----------------------------------------- |
| 按工作流步骤       | 需求是一个完整流程 | 下单 → 选商品/填地址/选支付/确认订单      |
| 按业务规则变体     | 同一功能多种规则   | 优惠 → 满减/折扣券/积分抵扣/组合优惠      |
| 按数据操作（CRUD） | 围绕一个数据对象   | 地址管理 → 新增/编辑/删除/设默认          |
| 按角色视角         | 多角色用同一功能   | 订单 → 用户看订单/商家处理订单/运营查数据 |
| 按复杂度递进       | 有简单版和完整版   | 搜索 → 关键词/筛选/搜索建议/搜索历史      |

粒度校准：拆出 <3 个故事时列出隐藏的子流程；>20 个时按 Epic 边界重切；单个故事估算 >8 点必须继续拆。

### 故事格式

每个故事：标题（动词开头）、角色/需求/价值、优先级（P0/P1/P2）、估算、验收标准（至少 1 条正常流程 + 1 条异常流程，Given-When-Then 带具体值——"Given 用户已登录且余额≥100，When 支付 100，Then 余额减 100 且订单状态变为已支付"，而不是"支付成功"）、依赖（无则写"无"）、可选技术备注。

### INVEST 门（每个故事六项全过）

- **Independent**：删掉这个故事，其他故事还能独立交付吗？循环依赖的合并或重拆。
- **Negotiable**：写的是"做什么"还是"怎么做"？删掉实现细节。
- **Valuable**：交付后用户能感知到价值吗？纯技术重构挂到用户可感知的功能上。
- **Estimable**：团队 5 分钟内能给出一致估算吗？分歧大说明需求不清，先澄清再估。
- **Small**：一个 Sprint 内能完成吗？不能就继续拆。
- **Testable**：QA 能照 AC 直接写测试用例吗？不能就补边界值和预期结果。
